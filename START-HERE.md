# PEG HR LMS — кратко для разработчика

Система онбординга новых сотрудников сети **Pingwin Premium** (рестораны, боулинг,
караоке). Здесь и описание логики, и **рабочий прототип**, который её реализует.

---

## Что делает система

Новичок заходит с телефона:

1. **Пре-онбординг** — материалы о компании (кто мы, площадка, обязанности,
   welcome-видео). Тестов нет, нужно просмотреть всё.
2. **Стажировка** — офлайн, 3–5 дней. HR нажимает **«Стажировка пройдена»** —
   открывается онбординг. Не прошёл → профиль удаляется.
3. **Онбординг** — траектория должности: блоки → уроки. Урок = **материал + тест**.
   Строго по порядку, всё обязательно, дедлайн 14 дней.
4. **Аттестация** — финальный тест по всем блокам. Сдал → статус «онбординг завершён».

HR с компьютера: ведёт сотрудников, собирает контент в конструкторе, смотрит
воронку. На телефоне у HR — мини-версия (список, карточка, кнопка стажировки).

Этапы сотрудника: `стажёр → онбординг → завершил → архив`.

## Запустить прототип

```bash
cd prototype
npm install     # ставит и бэкенд, и фронт
npm run dev     # API :3001 + приложение :5173
```

- Приложение — **http://localhost:5173**
- Swagger UI (живой API) — **http://localhost:3001/docs**

Прод-режим (один процесс отдаёт и API, и фронт — так же, как на сервере):

```bash
npm run build && npm start      # всё на :3001
```

Как выложить онлайн (Render / Docker / туннель) — `DEPLOY.md`.

Нужен Node 20.11+ (проверено на 24). БД создаётся сама и наполняется демо-данными
(~16 сотрудников на разных этапах, две готовые траектории — официант и кассир).

**Демо-аккаунты и сценарий показа — прямо на экране входа.** Пароль = логин + `123`
(например `hr` / `hr123`). Внизу служебная панель **DEMO**: перемотка даты,
журнал событий, сброс демо.

## Ключевые решения в логике

- **Урок = материал + тест.** Урок пройден, когда материал засчитан и тест сдан.
  Попытки не ограничены, пересдача сразу — состояния «провалил» нет.
- **Два гейта открывают онбординг:** пройден весь пре-онбординг И HR подтвердил
  стажировку кнопкой. Порядок между ними не важен, нужны оба.
- **Снимок траектории.** При открытии онбординга структура (блоки, уроки,
  материалы, тесты, вопросы с ответами) замораживается сотруднику. Дальше он
  учится только по своей копии — правки каталога **не могут сломать того, кто уже
  в пути**; они достаются только новым назначениям.
- **Просмотр видео проверяет сервер**, не клиент: копится `video_pct`,
  «отметить пройденным» отдаёт `422`, если не досмотрено.
- **Часовой пояс `Asia/Almaty`** — не UTC, иначе даты и дедлайны съезжают на день.
- **Журнал действий HR** — кто завёл, отметил стажировку, сбросил пароль, архивировал.
- Всё, что HR делает с контентом, проходит проверку полноты перед публикацией.

## Проверки (сквозные тесты)

При запущенном сервере, из `prototype/server`:

```bash
npx tsx scripts/e2e-check.ts      # весь путь сотрудника: найм → аттестация
npx tsx scripts/e2e-builder.ts    # конструктор: создание, валидация публикации
npx tsx scripts/e2e-snapshot.ts   # снимок: ломаем каталог — учащийся всё равно доходит
npx tsx scripts/e2e-guards.ts     # тупики: сломанная траектория не пускает новых, починка догоняет ждущих
npx tsx scripts/e2e-hr-actions.ts # возврат из архива, продление срока, пауза онбординга
```

## Если будешь интегрировать

Подробно — `prototype/README.md`, раздел «Интеграция в платформу коллеги».

**Переносится как есть:**
- `server/src/domain.ts` — ядро: гейты, движок разблокировки уроков, аттестация
- `server/src/snapshot.ts` — снятие и чтение снимка траектории
- `server/src/db.ts` (константа `SCHEMA`) — схема БД, прямой перевод в миграции
- `openapi.yaml` — контракт, ему точно соответствуют `server/src/routes/*`

**Заменить на платформенное:**
- `auth.ts` — сейчас самоподписанный HMAC-токен, у вас свои сессии/JWT
- `db.ts` — сейчас `node:sqlite`, у вас свой драйвер (Postgres и т.п.)
- хранилище файлов — сейчас только `file_url`, файлов нет

**Выкинуть целиком:** `routes/dev.ts`, `clock.ts`, `events.ts`, `/demo/accounts` —
это демо-часы, журнал событий и тестовые аккаунты, в прод не идут.

## Открытые вопросы

В конце `SPEC.md` (раздел «Требуют решения»):

1. **Повторный приём невозможен** — телефон уникален среди всех, включая архивных,
   а повторный приём = новый профиль. Нужно решение.
2. **Онбординг нельзя поставить на паузу** (болезнь, отпуск) — дедлайн идёт всегда.
3. **Список сотрудников без пагинации** — нормально для пилота, не для масштаба.
